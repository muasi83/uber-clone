Here's your reusable cheat-sheet. Save it — it covers every future update, code-only or with DB changes.

Setup (once per PowerShell window)
# Go to the backend folder
cd C:\Users\User\Desktop\Flutter\Chat\chatserver

# Store the database address (from Render → Postgres → Info → External Database URL)
$env:DATABASE_URL = "postgresql://PASTE-YOUR-URL-HERE"

# Your live backend address (for smoke tests)
$B = "https://YOUR-RENDER-URL.onrender.com"
Purpose: puts you in the right folder and saves the two addresses you'll reuse below. Setting a variable prints nothing — that's normal.
Case A — Code change only, no database change
# 1) Send the code to GitHub (Render auto-detects and rebuilds, ~5-10 min)
git push origin master
Purpose: this is the entire deployment. Render builds the Docker image and restarts the service itself.
# 2) Confirm it went through (your local branch matches GitHub = pushed)
git status -sb
Purpose: proves the push succeeded. Then check Render → Events until status is Live.
Case B — Code change WITH database change (like this release)
# 1) Back up the live database first (your safety net)
pg_dump "$env:DATABASE_URL" -Fc -f chat_db_backup_BEFORE_CHANGE.dump
Purpose: if anything goes wrong, this file restores everything.
# 2) Confirm you're on the right database (MUST show rides + driver_profiles)
psql "$env:DATABASE_URL" -P pager=off -c "\dt *rides*"
psql "$env:DATABASE_URL" -P pager=off -c "\dt driver_profiles"
Purpose: proves you're connected to the production DB and the tables exist. If these don't show, STOP — wrong database.
# 3) Run the migration file (replace with the new file name each release)
psql "$env:DATABASE_URL" -f src/main/resources/db/migration/V004__service_tier.sql
Purpose: adds/changes the columns. Always BEFORE pushing the code — new code querying missing columns crashes.
# 4) Verify the migration actually applied
psql "$env:DATABASE_URL" -P pager=off -c "SELECT column_name FROM information_schema.columns WHERE table_name='rides' AND column_name IN ('matched_tier','was_upgraded','upgrade_stage');"
Purpose: proves the columns exist. (Swap in whatever the new column/table names are for future releases.)
# 5) Now push the code — Render rebuilds on its own
git push origin master
Purpose: deploys the build that uses the new columns. Watch Render → Events until Live.
# 6) 30-second live check — request any ride as a rider
Purpose: confirms the new build talks to the migrated DB correctly. If the app works, you're done.
If it goes wrong
# Reedploy the last good version without pushing anything:
Render dashboard → your service → Deploys → find the previous successful deploy → Redeploy. Purpose: instant rollback of code while you investigate.
# If the migration itself was the problem, restore the backup (rare, last resort):
pg_restore -d "$env:DATABASE_URL" -c chat_db_backup_BEFORE_CHANGE.dump
Purpose: puts the database back exactly as it was. Only needed if a migration corrupted data — our idempotent scripts make this very unlikely.
The rule to remember
Database first, code second, verify third.
Migration → push → check Live → test one ride. In that order, every time, and Render updates can never surprise you.
